本文档记录 MaxKB `v2.10.3-lts` 中大语言模型和向量模型的接入、中文问答、文本向量化、
知识库检索及边界行为验证结果。本文档只保存可共享的配置原则和测试数据，不记录 API Key、
模型密钥、管理员密码或其他凭据。

## 一、任务目标与边界

4C01 的验证目标如下：

- 接入至少一个可用的大语言模型；
- 接入至少一个可用的向量模型；
- 根据实际效果判断是否需要重排模型；
- 验证中文对话生成、文本向量化、知识库检索和引用来源；
- 从兼容性、回答效果、Token 消耗、响应速度和部署条件等方面比较候选模型；
- 形成模型选型建议，为后续 MaxKB 正式工作流和后端适配提供依据。

本任务只验证 MaxKB 内部的模型与知识库能力，不提前实现 4C03 的正式工作流，也不把
4C04 的业务后端适配器调用作为完成条件。MaxKB 应用的正式发布标识、API 认证方式和
请求响应契约应在 4C03 完成后由 4C04 继续确认。

本轮验证同时覆盖了 4A01 中此前待完成的模型配置、测试知识库、测试应用、基础问答、
检索结果和引用来源检查。

## 四、测试知识库与统一配置

### 4.1 测试材料

测试知识库只上传了人工编写的 `4C01-test-corpus.md`，全部内容均为虚构测试数据，不代表
真实项目、机构或统计结果。文档共 `701` 个字符，向量化后形成 `4` 个分段：

| 分段 | 核心事实 |
|---|---|
| 文档说明 | 声明测试内容为虚构材料 |
| 青舟桥梁健康监测 | 误报率从 `14.2%` 降至 `4.8%`；采用零点校准、温度补偿和人工巡检交叉验证组成的三阶段校准法 |
| 岚田智能灌溉 | 主要灌溉触发阈值为 `23%`；用水量下降 `31%`，未出现明显减产 |
| 星港物流路径优化 | 燃油消耗下降 `12.6%`；每周超时任务从 `18` 次降至 `7` 次 |

### 4.2 检索和问答配置

| 项目 | 本轮配置 |
|---|---|
| 检索模式 | 向量检索 |
| 相似度阈值 | `0.45` |
| 引用分段数 | `TOP 3` |
| 向量模型 | `text-embedding-v4`，`1024` 维 |
| 重排模型 | 关闭 |
| 基础单轮测试 | 使用新会话，在启用问题优化前完成 |
| 多轮测试 | 历史聊天记录为 `1`，开启问题优化 |
| 边界测试 | 加入通用证据判断规则后复测，用于观察边界行为 |
| 模型对比原则 | 除被测大语言模型外，其余知识库、检索和提示词配置保持一致 |

阈值 `0.45` 是面向当前四分段测试材料的临时基线，不是生产环境最终参数。直接事实问题
存在约 `0.478` 至 `0.539` 的正确与干扰结果分隔区间，但多案例综合问题的相关分段分数
最低约为 `0.452`。因此本轮没有采用只适合直接事实问题的约 `0.52` 阈值，而是优先保留
多分段召回能力。正式阈值需要基于真实数据集继续评测。

### 4.3 回答约束原则

测试应用要求模型仅依据检索结果回答，并按以下通用规则处理边界情况：

1. 检索结果明确支持问题前提时直接回答；
2. 检索结果明确与问题前提冲突时指出错误并说明正确事实；
3. 资料只是没有提及时，表述为“知识库中没有显示……”，不把未提及推断为否定；
4. 资料不足、冲突或无法判断时明确说明依据不足；
5. 不编造案例、方法、数字或结论。

这些规则用于描述证据判断原则，不针对每一种边界问题逐条堆叠提示词。更复杂的证据核验
和流程控制应在 4C03 的正式工作流中实现。

## 五、知识库命中测试

命中测试先将阈值临时设为 `0`，观察全部四个分段的相似度，再确定本轮临时阈值。

| 编号 | 测试意图 | 正确结果相似度 | 其他结果最高相似度 | 结果说明 |
|---|---|---:|---:|---|
| 1 | 询问误报率降至 `4.8%` 的案例和方法 | `0.539` | `0.470` | 正确分段排名第一 |
| 2 | 询问农田项目触发阈值和节水效果 | `0.703` | `0.382` | 正确分段排名第一 |
| 3 | 询问驾驶员夜间任务和超时改善 | `0.595` | `0.478` | 正确分段排名第一 |
| 4 | 汇总三个案例的价值要求 | 不适用 | `0.515`、`0.487`、`0.452`、`0.303` | 前三个案例分段均为相关结果，不应只认定一个“正确分段” |
| 5 | 询问材料中不存在的人脸识别准确率 | 无正确结果 | `0.421`、`0.404`、`0.388`、`0.374` | 在 `0.45` 阈值下应无引用结果 |

验证结论：中文文本向量化成功；向量检索能够区分三个案例；直接事实问题的正确分段均排在
第一位；无依据问题能够被临时阈值过滤；多案例综合问题需要保留多个相关分段。

## 六、大语言模型对比结果

下表中的 Token 和耗时均来自 MaxKB 调试界面的单次人工记录。不同模型的分词口径、回答
长度、云服务负载和网络情况可能不同，因此这些结果用于本轮相对比较，不代表长期服务等级
或精确账单。

### 6.1 单轮问题

| 编号 | 测试内容 | Qwen Token | Qwen 耗时 | DeepSeek Token | DeepSeek 耗时 | 结果 |
|---|---|---:|---:|---:|---:|---|
| 1 | 误报率和三阶段校准法 | `910` | `7.33 s` | `712` | `1.94 s` | 均可依据正确分段回答 |
| 2 | 灌溉阈值和节水效果 | `504` | `5.61 s` | `395` | `2.16 s` | 均可依据正确分段回答 |
| 3 | 物流优化及改善结果 | `814` | `8.46 s` | `579` | `1.96 s` | 均可依据正确分段回答 |
| 4 | 三个案例的价值要求 | `971` | `11.56 s` | `944` | `3.98 s` | 可进行跨分段综合回答 |
| 5 | 知识库外的人脸识别结论 | 未记录 | `0.40 s` | 未记录 | `0.38 s` | 均返回知识库无依据 |

前四个问题合计：Qwen 为 `3199` Token，DeepSeek 为 `2630` Token，DeepSeek 少约
`17.8%`。包含第五个问题的总耗时分别约为 `33.36 s` 和 `10.42 s`，本轮 DeepSeek
约快 `3.2` 倍。

### 6.2 多轮指代问题

多轮测试使用以下连续问题：

1. “青舟桥梁健康监测案例解决了什么问题？”
2. “它体现了哪些思政要素？”

仅配置历史聊天记录时，两个模型都无法稳定确认第二轮“它”的指代对象。原因是历史记录
会传入最终回答模型，但知识库检索仍可能直接使用含糊的当前问题。开启 MaxKB“问题优化”
后，第二轮问题会在检索前结合历史记录改写为包含明确案例名的问题，指代问题得到解决。

| 轮次 | Qwen Token | Qwen 耗时 | DeepSeek Token | DeepSeek 耗时 |
|---|---:|---:|---:|---:|
| 第一轮 | `1381` | `18.96 s` | `763` | `4.29 s` |
| 第二轮 | `1275` | `8.09 s` | `1171` | `3.17 s` |
| 合计 | `2656` | `27.05 s` | `1934` | `7.46 s` |

多轮测试中，DeepSeek 少约 `27.2%` Token，总耗时约为 Qwen 的 `27.6%`。问题优化会
增加一次模型调用，因此只应在需要结合上下文改写检索问题时启用，并将该开销计入正式应用
的成本与响应时间评估。

### 6.3 边界问题

| 类型 | 测试目的 | Qwen 结果 | DeepSeek 结果 |
|---|---|---|---|
| 表达变换 | 使用不同措辞询问桥梁项目如何降低误报警 | 正常回答；`1255` Token，`18.74 s` | 正常回答；`927` Token，`4.79 s` |
| 错误前提 | 询问岚田智能灌溉是否采用三阶段校准法 | 初始回答知识库无依据；加入证据判断规则后，记录中仍未完成预期纠正；`1962` Token，`25.86 s` | 初始回答知识库无依据；加入证据判断规则后改为“知识库中没有显示……”的保守表述；`786` Token，`2.95 s` |
| 跨案例比较 | 比较节水 `31%` 和燃油下降 `12.6%` 分别属于哪个案例 | 回答正确；`1832` Token，`21.59 s` | 回答正确；`1578` Token，`6.33 s` |

三个边界问题合计：Qwen 为 `5049` Token、`66.19 s`；DeepSeek 为 `3291` Token、
`14.07 s`。DeepSeek 少约 `34.8%` Token，本轮总耗时约为 Qwen 的 `21.3%`。

边界测试阶段已经调整回答约束，因此其 Token 和耗时不能与基础单轮测试合并成严格受控的
统一性能基准。两个模型在同一个边界问题中使用相同的当时配置，数据可以作为该问题下的
相对表现参考。

错误前提问题揭示了一个通用限制：知识库明确记录某方法属于另一个案例，并不必然等价于
明确记录当前案例“没有采用”该方法。回答系统应区分“明确冲突”“未提及”和“证据不足”。
如果纠正所需的另一个案例分段没有被检索到，模型不应凭记忆补充归属关系。

## 八、结论与已确认选型

本轮已完成以下验收：

- DeepSeek 和阿里云百炼大语言模型均能通过 MaxKB 接入并完成中文问答；
- 阿里云 `text-embedding-v4` 能完成测试文档向量化和中文向量检索；
- 测试知识库、测试应用、基础问答、无依据回答和引用来源均已验证；
- 通过问题优化解决了多轮对话中指代不明确导致的检索偏差；
- 直接事实问题的正确分段均排名第一，当前没有引入重排模型的必要；
- 两个大语言模型的主要回答能力均满足本轮接入验证要求。

在当前小样本和单次人工测试条件下，`deepseek-v4-flash` 在 Token 消耗、响应速度和部分边界
问题表现方面整体优于 `qwen3.7-plus`。负责人已确认4C01当前选型：

1. 将 `deepseek-v4-flash` 作为后续正式工作流的首选大语言模型；
2. 保留 `qwen3.7-plus` 作为备用大语言模型和对照模型；
3. 使用 `text-embedding-v4`、`1024` 维作为当前向量模型；
4. 暂不接入重排模型，待真实语料检索评测显示排序不足时再决定。

以上是4C01阶段的已确认技术选型，不代表供应商、价格和检索参数永久锁定。后续如果真实
语料评测、服务稳定性、供应商价格或项目预算发生明显变化，应重新形成对比证据并由负责人
确认变更。

## 九、已知限制与后续输入

### 9.1 已知限制

- 测试语料只有一个人工文档和四个分段，不能代表真实案例库规模；
- 当前阈值 `0.45` 只适用于本轮测试材料，不能直接作为生产参数；
- Token 和响应时间均为人工单次记录，受回答长度、网络和云服务负载影响；
- 不同模型的 Token 统计口径可能不同，界面数据不等于供应商最终账单；
- 问题优化能够改善多轮指代，但会增加模型调用、Token 和延迟；
- 错误前提的纠正依赖相关纠正证据被成功检索，不能只通过不断增加提示词解决；
- 云模型依赖外部网络和供应商服务可用性，需要保留超时、降级和错误处理方案。

### 9.2 对后续任务的输入

4C03 正式工作流应继承或重新确认：

- 首选和备用大语言模型；
- 向量模型和维度；
- 问题优化的启用条件；
- 检索阈值、TOP 数量和是否需要重排；
- 无依据、错误前提、证据冲突和引用来源的回答策略；
- 模型超时、失败和供应商不可用时的降级行为。

4C04 应在 4C03 应用发布后，通过公开 API 接入已发布应用或工作流，并确认应用标识、认证
方式、超时、错误映射和请求响应契约。4C04 不应访问 MaxKB 内部数据库，也不应依赖其内部
Django 模块。

正式案例语料的批量评测、阈值调优、召回率和回答质量统计不属于本轮小样本4C01接入验证，
应在后续检索和问答评测任务中完成。
