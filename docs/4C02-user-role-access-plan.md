## 三、已确认的十项设计决定

| 编号 | 已确认决定 |
|---|---|
| D1 | 账号由平台管理员创建，首版不开放自助注册。 |
| D2 | 平台只设学生、教师、管理员三类角色，不单独设置审核员。 |
| D3 | 新账号默认为学生；教师身份只能由管理员授予或调整。 |
| D4 | 学生和教师可以使用已发布案例问答；教师和管理员可以使用 AI 案例生成。 |

## 四、账号与认证规则

### 4.1 账号生命周期

学生、教师和管理员都是自研平台账号，不是 MaxKB 用户。账号至少包含内部用户 ID、唯一登录名、
密码散列、角色、状态和必要审计信息。

管理员创建账号后，账号默认为学生；管理员可以授予教师身份、调整学生与教师角色、冻结账号和
重置密码。用户不能自行更改角色，普通用户也不能取得管理员权限。初始管理员的初始化方式、密码
规则和是否要求首次登录改密，在实现认证模块前另行细化。

### 4.2 登录与会话

1. 用户提交用户名和密码，后端同时检查密码和账号状态；
2. 校验成功后签发默认有效期 120 分钟的 JWT；
3. 前端通过 Bearer 令牌访问自研后端，并将令牌保存在内存或 `sessionStorage`；
4. 退出登录、令牌过期或认证失败时清除令牌，用户重新登录；
5. 后端在每个受保护请求中验证身份，并对敏感操作检查用户当前状态和角色。

首版不提供刷新令牌。JWT 中的角色不能作为敏感操作的唯一授权依据，因为账号可能在令牌有效期
内被冻结或调整角色。会话级保存也不能替代 XSS 防护；公开部署前应再评估短访问令牌、HttpOnly
刷新 Cookie、令牌轮换、注销撤销和 CSRF 防护。

### 4.3 授权原则

- 前端菜单和路由守卫用于改善交互，真正的安全边界在后端；
- 后端按照角色、资源归属和业务状态授权，教师只能维护自己有权处理的内容；
- AI 调用资格由自研后端判断，不能通过 MaxKB API Key 推断用户角色；
- 角色变更、账号冻结、密码重置和案例审核等关键操作应保留审计记录。

## 五、角色与业务权限矩阵

表中的“自己的案例”是指本人创建或被授予维护权的案例；具体状态约束由案例状态机继续细化。

| 功能 | 学生 | 教师 | 管理员 |
|---|:---:|:---:|:---:|
| 登录、个人信息和修改本人密码 | 允许 | 允许 | 允许 |
| 浏览、检索、收藏和问答已发布案例 | 允许 | 允许 | 允许 |
| AI 案例生成和本人生成历史 | 禁止 | 允许 | 允许 |
| 创建、编辑、导出和提交自己的案例 | 禁止 | 允许 | 允许 |
| 审核案例并填写通过或驳回意见 | 禁止 | 禁止 | 允许 |
| 维护全部案例，包括编辑、上下架、删除和导入导出 | 禁止 | 禁止 | 允许 |
| 管理分类、标签、用户和平台统计 | 禁止 | 禁止 | 允许 |
| 管理 MaxKB 模型、知识库、应用或 API Key | 禁止 | 禁止 | 默认禁止 |

MaxKB 管理由指定技术运维人员承担。即使同一人兼任平台管理员，也应分别授予两套权限。

## 六、页面、路由与访问规则

### 6.1 路由分区

任务3可以调整实际 URL，但页面至少应按下列访问级别分区：

| 路由分区 | 页面示例 | 允许访问者 |
|---|---|---|
| 公共区 | 登录页 | 未登录用户及需要重新登录的用户 |
| 登录共享区 | 首页、案例列表、案例详情、搜索、收藏、个人中心、案例问答 | 学生、教师、管理员 |
| 教师工作区 | AI 生成、生成历史、我的案例、案例编辑、手动上传、提交审核 | 教师、管理员 |
| 管理区 | 审核队列、全量案例、分类标签、用户管理、统计 | 管理员 |

路由元数据应统一表达“需要登录”和“允许角色”。后端接口必须执行同等或更严格的权限检查。

### 6.2 访问异常处理

| 场景 | 前端行为 | 后端行为 |
|---|---|---|
| 未登录访问受保护页面 | 引导至登录页，并避免展示受保护数据 | 返回统一未认证响应 |
| 已登录但角色不足 | 展示无权限页面或提示，不进入目标功能 | 返回统一禁止访问响应 |
| 令牌过期或无效 | 清除会话令牌并引导重新登录 | 拒绝请求，不使用过期身份继续处理 |
| 账号被冻结 | 结束当前会话并提示联系管理员 | 即使令牌尚未到期也拒绝受保护请求 |
| MaxKB 暂时不可用 | AI 功能提示暂不可用，非 AI 页面继续工作 | 隔离 AI 调用失败，不影响非 AI 业务接口 |

4F04 必须验证直接访问受限路由、绕过菜单调用接口、令牌过期和账号冻结，不能只检查菜单是否
隐藏。

## 七、自研系统与 MaxKB 权限边界

| 自研系统负责 | MaxKB 负责 |
|---|---|
| 平台账号、登录、密码、角色、状态和审计 | 模型、向量模型和知识库 |
| 页面与接口授权、案例归属和状态检查 | 检索、工作流和应用发布 |
| 案例创建、版本、审核、发布、收藏和管理 | 按已发布应用执行 AI 任务 |
| 判断用户能否问答或生成，并记录业务调用 | 提供服务端应用 API Key |

正式访问链路为：

```text
学生／教师／管理员浏览器
        ↓ 平台 JWT
自研 FastAPI 业务后端
        ↓ MaxKB 应用 API Key
MaxKB 已发布应用／工作流
```

关键约束如下：

- 浏览器只认证到自研后端，不持有 MaxKB API Key，也不把公开访问链接作为正式入口；
- MaxKB API Key 是服务身份，用户角色和调用资格必须由自研后端检查；
- 首版不为每个平台用户创建对应的 MaxKB 用户，避免维护两套账号生命周期；
- 平台业务管理员不会自动获得 MaxKB 管理权；
- 4C04 如需传递会话标识，只使用受控内部标识，不传递密码、平台 JWT 或无关个人信息。

只有未来明确需要多学院工作空间、终端用户直登 MaxKB、增强 RBAC 或 SSO 时，才重新评估
X-Pack 和账号映射方案。
