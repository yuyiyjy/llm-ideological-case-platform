# MaxKB 稳定基线与使用规范

> 对应任务：4A01、4A03
> 
> 基线状态：已固定

本文档记录项目当前采用的 MaxKB 源码和 Docker 镜像基线、已完成验证、待验证范围
以及后续升级规则。MaxKB 作为独立 AI 能力服务运行，不并入自研业务数据库，也不修改或导入其 Django 业务代码。

## 一、基线决定

已确认使用 MaxKB `v2.10.3-lts` 作为当前稳定基线。

| 项目 | 固定值 |
|---|---|
| MaxKB 版本 | `v2.10.3-lts` |
| 源码标签 | `v2.10.3-lts` |
| 源码提交 | `dcab5d0ef4275756ce9fc1f63360f241fe7adc1c` |
| Docker 镜像 | `registry.fit2cloud.com/maxkb/maxkb:v2.10.3-lts` |
| Docker 镜像摘要 | `sha256:aab30eadbaba537fcc4ac80775bac72d7b2b477f050a39cbcbf6d8aee75ec949b3` |
| 部署方式 | 独立 Docker 容器 |
| 源码使用方式 | 版本核对和结构参考，不进行项目内二次修改 |

镜像标签便于人工识别，镜像摘要用于精确确认实际内容。后续不能只记录或部署
`latest`，因为该标签会随新版本发布而变化。

官方参考：

- [MaxKB v2.10.3-lts 源码](https://github.com/1Panel-dev/MaxKB/tree/v2.10.3-lts)
- [MaxKB Docker 镜像标签](https://hub.docker.com/r/1panel/maxkb/tags)
- [MaxKB 在线安装说明](https://maxkb.cn/docs/v2/installation/online_installtion/)

## 二、选择该基线的原因

- LTS 标签比持续变化的 `v2` 开发分支更适合作为团队协作基线；
- 源码标签和 Docker 镜像都能明确指定版本；
- 固定提交和镜像摘要后，可以在不同成员环境中复核实际版本；
- 项目当前通过配置、工作流和 API 使用 MaxKB，不需要维护自定义 MaxKB 分支；
- 升级可以作为独立变更评估，不与业务后端日常开发自动耦合。

## 三、团队统一基线要求

所有成员使用 MaxKB 时，应满足以下一致性要求：

- 源码核对以 `v2.10.3-lts` 标签和固定提交为准；
- Docker 部署使用已固定的版本镜像，不使用 `latest`；
- 镜像内容应能通过摘要与本文档记录进行核对；
- MaxKB 保持独立部署，不加入自研业务后端进程；
- 不修改 MaxKB 源码，不维护项目专用的 MaxKB 分支；
- 源码目录、容器名称、主机端口和数据存储位置可以因运行环境而异；
- 环境差异不得改变 MaxKB 版本、镜像基线和系统边界。

如果只需要运行和配置 MaxKB，可以直接使用固定 Docker 镜像，不要求每位成员都在
检出完整源码。需要核对源码结构或排查版本行为时，再检出对应标签。

## 四、源码结构与使用边界

当前版本的主要目录职责如下：

- `ui/`：MaxKB 前端；
- `apps/`：Django 后端及业务应用；
- `installer/`：镜像构建和容器启动脚本。

这些目录只用于理解 MaxKB 的实现、确认接口行为和辅助排查问题。项目业务功能应优先
通过 MaxKB 配置、工作流和公开 API 实现，不直接导入其内部模块，也不访问其内部数据库。

## 五、部署与配置原则

- MaxKB 使用独立 Docker 容器运行；
- 当前项目仓库的 `infra/compose.yaml` 不负责启动 MaxKB；
- 容器内部服务端口为 `8080`，主机映射端口根据运行环境中的端口占用情况确定；
- `/opt/maxkb` 中的运行数据必须挂载到持久化目录或 Docker Volume；
- MaxKB 运行数据不得保存在本项目仓库中；
- MaxKB 数据库与自研业务 PostgreSQL 必须保持独立；
- 业务后端通过各自环境中的 `MAXKB_BASE_URL` 连接实际 MaxKB 地址；
- API Key、模型密钥和管理员凭据只能保存在受控配置或受控部署环境中；
- 不得把真实凭据写入文档、代码、截图、提交或前端环境变量。

容器名、主机端口和数据目录属于环境配置，不构成共享技术基线。团队协作时只需记录
其配置规则，不要求所有成员使用相同的环境路径或容器名称。

## 八、升级规则

更换 MaxKB 版本属于共享技术基线变更，必须：

1. 说明升级原因；
2. 记录旧版本和新版本；
3. 检查官方更新说明和兼容性；
4. 先使用独立容器和独立数据副本验证；
5. 回归知识库、模型、应用、工作流和 API；
6. 更新源码提交、镜像标签和镜像摘要；
7. 确认回退方式后再替换团队稳定基线。

未经确认，不得把 `latest`、`v2` 开发分支或其他新版本自动视为项目稳定版本。

容器、数据目录或 Docker Volume 的删除不属于普通升级步骤。执行删除或迁移前必须先
确认数据、备份、回退方式和对其他成员的影响。
